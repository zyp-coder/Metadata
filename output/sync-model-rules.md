# 同步模型规则说明书 — 域 14 产品档案（ITEM）

> 目的：把同步引擎的**隐式规则**显式化，让"系统认为的模型关系"可查看、可审核。
> 数据来源：`backend/apps/archive/views.py`（引擎代码）+ 数据库实际配置（2026-08-08 导出）。
> 审核结论 → 决定是否把"隐式规则"升级为"显式模型定义层"。

---

## 一、总览：档案 = 物化大宽表

- **不是物理宽表、不是 SQL 视图**：所有档案共用一张 `ArchiveRecord` 表，每条记录 = 一个 JSON（`{字段code: 值}`），是同步时从源库多张表拉数、折叠合并后的**物化快照**。
- **双层存储**：`source_data`（源同步底层，每次同步整层替换）+ `manual_data`（人工覆盖层）+ `data`（写时合并物化结果，供展示/API/计算）。
- **粒度 = 主数据粒度**：一条记录 = 一个主数据实体（如一个物料），**不保留源库的 1:n 明细粒度**（多价格只留一条）。
- **审计**：`ArchiveChangeBatch`（批次）+ `ArchiveChangeDetail`（明细，含字段级 old→new）+ `ArchiveRecordVersion`（版本快照，变更才 +1）。

## 三、同步引擎规则（10 条，代码事实）

### R1 档案主键与匹配通道
- 档案主键 = 主表主键字段的 schema code（`MTL_ID`）。
- 匹配通道 = 该标准字段的**全部成员列**（22/24/28 三表的 MATERIAL_ID）：任意一张表行数据里只要含有任一成员列，就能匹配到档案记录。
- 匹配 key 构建：`(MTL_ID 值,)`，任一成员列的值都可用于定位记录；全空 → 跳过。

### R2 字段映射（写入映射 code_to_physical）
1. 组合字段已设主字段 → **只映射主字段成员**（数据源头唯一，其余成员不写底层，仅一致性检查）。
2. solo 字段：Field.code 命中 schema code → 映射到该表的 physical_name 列。
3. 组合字段未设主字段 → 全部成员映射（多源覆盖，后者胜）。
4. 匹配通道列（非主成员外键）**只用于构建 key，不写入档案**（防多源覆盖）。
5. 他表同名兜底仅限主键列，非主键同名列禁止写入（BUG-2026-0805-01：他表同名空列偷渡清空）。

### R3 表分类与处理入口（同步时逐表判定）
| 类型 | 判定 | 处理函数 | 行为 |
|------|------|---------|------|
| 主表 | is_primary | `_upsert_records_from_rows` | 全字段直写；**无匹配可创建新记录** |
| 直连表 | 有物理列映射档案主键（24/28） | `_upsert_records_from_rows` | 直写本表字段；匹配不到**跳过不创建**（外键引用非独立实体） |
| 一级中转表 | 有 source FieldMapping（25/27） | `_upsert_dimension_via_mapping` | 经映射跳到目标表行 → 提取主键 → 折叠/展开写入 |
| 多级链式表 | 无 source 映射（26） | BFS `_build_mapping_chain` | 沿 FieldMapping 无向等值图找"能映射档案主键的表"路径（深度≤5 防环），逐级透传 |

### R4 折叠规则（1:n 取首条，关键！）
- 同 key 多行（如一个物料在表 28 有多条价格）→ **保留排序后最后一行**（确定性折叠），其余丢弃，`cardinality_fold_count` 计数告警（实测 12,044 次折叠）。
- 排序键 = 该表主键物理列（如 28.FID）。
- **这是"明细丢失"的直接原因**：业务要"一个物料全部价格"，现规则只留一条。

### R5 展开传播（1 组 → N 物料）
- 分组属性（25/26）沿关联链传播到组内**全部**物料记录：每条物料都冗余带 GROUP_NO/GROUP_NAME/GROUP_DESC（查得快，不实时 join）。
- 与折叠相反方向：折叠 = N 行 → 1 值；展开 = 1 行 → N 记录同值。

### R6 写入与版本
- 本表映射字段 → 合并进 `source_data`（零比对整层替换语义）→ `data` = 底层 + 人工覆盖层合并物化。
- 与旧 data 有差异 → `version+1` + 版本快照 + 变更明细（字段级 old→new）。
- 无差异 → 仅落底层（批量 bulk_update，防全量模式逐条 UPDATE）。
- 维度字段空值不写（防清空已有值）；停用记录也参与匹配（源端重现自动复活）。

### R7 变更日志
- 本轮有变更才建批次（零变更无噪声）；来源分 `sync/manual/api`。
- 明细含：记录标识 / 记录信息快照（组合字段值）/ 变更类型（新增/修改/停用/复活）/ 字段级变化 / 版本 before→after。
- 刚创建记录被后续表合并时不重复记"修改"（防首次全量 20 万重复明细）。

### R8 一致性检查（告警不阻断）
- 组合字段非主字段成员的值 vs 主字段值比对（跨表同义字段是否一致），不一致仅告警 + 采样，数据以主字段为准。
- 检查结果落 `ConsistencyIssueHistory` 历史轨迹。

### R9 停用清扫与复活
- 源侧删除 → 记录标记停用（status=deleted, sync_status=stale），**不物理删除**。
- 安全闸门：任一表同步出错或无主键 → 跳过清扫（防源库瞬时故障误停用）。
- 停用清扫不动数据层，无版本变动。
- 源端重现 → 自动复活（版本+1 + 变更明细"复活"）。

### R10 计算字段
- 物化后重算：`computed_service` 从记录 data 构建 context（键 = `表名.Field.code`），公式按 `{表名.字段code}` 引用。
- DAG 排序（依赖其他计算字段也支持）；配置表函数（MAP_VALUE/MAP_ORDER）查 `ConfigTable`。
- 引用不到字段 → 该计算字段静默失败（2026-08-10 修：公式写物理名导致 7 个全失败）。

## 五、与"显式模型"设想的差距（你的设计 vs 现状）

| 你的设想 | 现状 | 差距 |
|---------|------|------|
| 模型关系 = 系统里可见的一份定义 | FieldMapping/StandardField 有配置，但"每表怎么匹配/折叠/展开"是代码隐式规则 | 说明书不可见、不可校验；8-10 分组字段全 0 就是隐式规则漏的 |
| 同步按模型逻辑执行 | 引擎按 R1-R10 执行，效果一致 | 无（执行正确） |
| 审计按模型逻辑追踪 | 记录级审计完整；**明细行无独立身份** | 保留明细后，行的增删改无法追踪 |
| 档案 = 大宽表 | ✅ 已实现 | 无 |
| API/查询从模型逻辑输出 | API 直接读 data；明细场景需补投影规则 | 明细落地时需统一 |
