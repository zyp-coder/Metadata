## 简介
本文件围绕 FieldMapping（字段映射）实体，给出面向数据库设计的完整说明。内容涵盖：
- 源表/源字段到目标表/目标字段的映射配置与约束
- 唯一性约束、双向查询支持与级联删除策略
- **新增的JOIN类型配置**：支持LEFT JOIN和INNER JOIN操作
- 在数据同步与转换中的作用与使用场景
- 完整的字段说明、映射配置示例与常见问题处理

该设计用于主数据建模域内不同表之间的字段关联表达，支撑 AI 推断、人工维护、以及后续的数据同步与一致性校验等流程。

## 详细组件分析

### 字段映射模型（FieldMapping）
- 字段说明
  - source_table：外键指向 Table，表示映射的源表
  - source_field：外键指向 Field，表示映射的源字段
  - target_table：外键指向 Table，表示映射的目标表
  - target_field：外键指向 Field，表示映射的目标字段
  - relation_type：关系类型（reference/detail），控制数据同步行为
  - **join_type：连接类型（left/inner），控制SQL JOIN操作类型**
  - conditions：结构化筛选条件，支持复杂WHERE子句
  - created_at：创建时间
- 唯一性约束
  - 通过 unique_together 对 (source_table, source_field, target_table, target_field) 进行唯一性约束，确保同一组映射不会重复创建
- 级联删除策略
  - 所有外键均设置为 on_delete=CASCADE，当源/目标表或字段被删除时，对应的映射记录也会被级联删除，保证数据一致性
- 反向查询支持
  - 通过 related_name='source_mappings' 和 'target_mappings'，可从 Field 和 Table 反向查询与其相关的映射集合，便于构建双向查询能力

**新增JOIN类型功能**：
- JoinType枚举：支持LEFT和INNER两种连接类型
- LEFT JOIN：保留无匹配行，适用于需要保留所有源数据的场景
- INNER JOIN：仅保留匹配行，适用于严格匹配的数据同步场景
- 默认值：LEFT JOIN，确保向后兼容性

### AI 推断映射（ai_service.infer_mappings）
- 功能概述
  - 收集域内所有活跃表与字段
  - 获取已存在的映射（去重），避免重复建议
  - 启发式匹配：同编码且非双主键的字段组合优先建议
  - 可选 LLM 智能分析：根据表结构与字段信息生成更丰富的建议，合并去重后返回
- 输出结构
  - 每条建议包含 source_table_id、source_field_id、target_table_id、target_field_id、confidence、reason

## 性能考量
- 查询优化
  - 视图集使用 select_related 预加载四个外键，减少 N+1 查询
  - 过滤条件基于索引友好的字段（如 table_id、domain_id）
  - **JOIN类型字段为简单字符串比较，不影响查询性能**
- 写入优化
  - 唯一性约束由数据库层保障，避免业务层重复判断开销
  - 批量创建映射时建议分批提交，降低事务压力
  - **新增join_type字段有默认值，减少插入时的计算开销**
- 缓存与降级
  - AI 推断失败时回退到启发式匹配，保证可用性
  - **JOIN类型配置在前端缓存，减少不必要的API调用**

## 故障排查指南
- 唯一性冲突
  - 现象：创建映射时报唯一性冲突
  - 排查：确认是否存在相同 (source_table, source_field, target_table, target_field) 的记录
  - 解决：删除重复映射或调整映射端点
- 级联删除影响
  - 现象：删除表或字段后映射丢失
  - 原因：外键 on_delete=CASCADE
  - 解决：在删除前清理相关映射或采用软删除策略（需扩展模型）
- 双向查询为空
  - 现象：按 table 参数查询无结果
  - 排查：确认 table 是否为 source_table 或 target_table
  - 解决：检查过滤条件与数据是否正确
- **JOIN类型相关问题**
  - 现象：数据同步结果不符合预期
  - 排查：检查映射的join_type配置是否正确
  - 解决：对于需要保留所有源数据的场景使用LEFT JOIN，对于严格匹配场景使用INNER JOIN

## 结论
FieldMapping 以简洁而严谨的模型设计，实现了表间字段映射的持久化与查询能力。**新增的JOIN类型配置功能进一步增强了数据同步的灵活性**，使得系统能够根据不同业务场景选择合适的连接策略。通过唯一性约束与级联删除，保证了数据一致性与完整性；通过反向查询与 API 过滤，提供了灵活的双向检索能力；结合 AI 推断与前端交互，显著降低了人工配置成本。该设计为后续数据同步、转换与一致性校验奠定了坚实基础。

### 映射配置示例
- 示例一：单字段映射（LEFT JOIN）
  - 源表：orders，源字段：customer_id
  - 目标表：customers，目标字段：id
  - JOIN类型：LEFT JOIN
  - 用途：订单与客户的一对多关联，保留所有订单即使客户不存在
- 示例二：联合主键映射（INNER JOIN）
  - 源表：order_items，源字段：composite（联合主键）
  - 目标表：products，目标字段：composite（联合主键）
  - JOIN类型：INNER JOIN
  - 用途：商品与订单项的多对多拆分映射，仅保留匹配的商品
- 示例三：条件映射
  - 源表：employees，源字段：dept_id
  - 目标表：departments，目标字段：id
  - JOIN类型：LEFT JOIN
  - 条件：department_status = 'active'
  - 用途：员工与部门的关联，仅考虑活跃部门

### 使用场景
- 数据同步
  - 依据映射关系将源系统数据同步至档案侧，确保字段对应一致
  - **通过JOIN类型控制数据保留策略：LEFT JOIN保留所有源数据，INNER JOIN仅保留匹配数据**
- 一致性校验
  - 对比源侧与档案侧字段值，发现差异并记录不一致项
  - **JOIN类型影响校验范围：LEFT JOIN检查所有源记录，INNER JOIN仅检查匹配记录**
- 关系可视化
  - 在 ER 图中展示表与字段间的映射连线，辅助建模与维护
  - **JOIN类型可通过前端界面直观查看和修改**

### JOIN类型使用指南
- **LEFT JOIN适用场景**：
  - 需要保留所有源数据的增量同步
  - 主从关系中从表可能缺失的情况
  - 历史数据归档，保留所有历史记录
- **INNER JOIN适用场景**：
  - 严格的数据一致性要求
  - 主键关联的精确匹配
  - 数据清洗和验证过程
- **配置建议**：
  - 初次配置建议使用LEFT JOIN，确保数据完整性
  - 生产环境可根据业务需求调整为INNER JOIN
  - 定期审查JOIN类型配置，确保符合业务逻辑
