# 项目规则（prjm 操作系统层）

以下规则在每次 AI 交互中强制生效，无论调用 reqa、darc、adqa 还是直接编码：

## 1. 先读上下文，再用 prjm 路由

每次会话开始：
1. 扫描项目目录：读 `.ai/constitution.md` + `.ai/session.md` + `.ai/route_index.md`
2. 有未完成任务 → 询问用户是否续接
3. 用 prjm 技能做任务路由：判断该做需求分析（reqa）、设计编码（darc）、对抗质疑（adqa，三个时点：方向锁定关/对抗验收/事故复盘）、还是文档/记录（prjm 直接处理），`AskUserQuestion` 确认后再执行

### 1.1 编码前置闸门（强制，堵"绕过技能直接改代码"）

**任何代码编辑动作之前，必须已经 prjm 路由，且已实际加载对应的执行技能**。不限于会话开始——会话中途每次收到"改代码/修 Bug/加功能/重构"类指令时，若尚未路由，先路由再动手：

1. 未经 prjm 路由 → **禁止直接编辑代码**（哪怕用户说"顺手改一下"）
2. 路由动作：判定走 reqa/darc/uxqa 哪个技能 → 用 `Skill` 工具真正加载该技能（不是 prjm 自己代办）→ 做"变更前三思"影响分析 → `AskUserQuestion` 确认 → 向 `.ai/.prjm-gate` 写入时间戳标记 → 才可编码
3. 仅以下情形可跳过路由：纯问答、纯文件读取、用户显式说"不用走流程直接改"

**物理闸门（Hook 硬拦截，不依赖 AI 自觉）**：项目已配置 `PreToolUse` hook（`.qoder/hooks/prjm-gate.sh`，匹配 `Write|Edit`）。任何代码文件的编辑，若 `.ai/.prjm-gate` 标记不存在或超过 30 分钟 → 编辑被直接拦截（exit 2）。因此上述第 2 步的"写标记"不是可选项——不写标记就真的改不了代码。纯文档/`.ai`/`output`/`.qoder` 不受限。

**自检回执（每次编码前必须显式输出一行）**：开始改代码前，先输出一句
`✅ 已经 prjm 路由 → 已加载 [reqa/darc/uxqa] 技能 → 用户已确认`
——若这三项不全，停下来补齐流程，不得动手。这句回执既提醒 AI 自己、也让用户一眼看到流程是否真走了。

> 违反此闸门（未路由/未加载技能就改代码）视为严重错误，等同违反 §8 禁止清单。

## 2. 决策锁定

已确定的实现决策（打包方式、协议、数据格式、构建工具、部署方式、目录结构/部署路径等）**禁止擅自更改**。

想做不同方式时 → 必须先询问用户说明：当前做法 → 想改成什么 → 原因。用户确认后才能执行。

## 3. 操作留痕（双层：主文件索引 + 模块详情文件，防 session.md 长成上下文炸弹）

每次回答结束时，分两层留痕（历史不删减，全部可检索）：

1. 索引行 → 追加到 `.ai/session.md`「功能索引」表（每轮一行，倒序）：

```
| 轮次 | 日期 | 模块 | 功能标签 | 一句话摘要 | 完整性 | 确认点 |
```

2. 详情条目 → 追加到 `.ai/session-details/<模块>.md`，标题格式 `### 第N轮（日期）标签：xxx`，内容含：读取/修改文件、变更摘要（如 `audit_timeout: 300→1800`，不要求行级 diff）、状态变更、遗留问题。跨模块任务详情写入主模块文件，索引行「模块」列列全所有涉及模块。

主文件 `session.md` 只放：当前会话状态（仅最近 3 轮保留详情）+ 功能索引表 + 未完成事项。**禁止**把逐轮长摘要堆进主文件——启动只读主文件，历史详情靠「模块+功能标签」按需 grep 加载。
功能标签用页面路径或功能域词（如 `/archive/记录编辑`、`同步引擎`、`计算字段`），保证可 grep 检索。
完整性字段记编码任务的 §5.1 硬回执结果（如 `闸✓记✓拓✓` 或 `⚠️拓-待补`）；非编码任务填 `N-A`。
确认点字段记本次任务 AskUserQuestion 次数与用户改向次数（格式 `3问/1改向`）：用户从未改向的确认点是减脂复盘的候选合并项；无确认点填 `0问`。

## 4. 知识库追加写

`.ai/constitution.md` 中的 Bug/决策**只追加不修改**。术语维护在 `output/darc/glossary.md`，同样只追加不修改。

**例外**：darc 日记的顶部「快照区」（当前整体架构/实现/已知问题）允许覆盖刷新为最新态；变更记录区仍只追加。STYLE_GUIDE.md 同理，骨架可刷新，变更历史追加。

## 5. 完成前自检清单

编码完成后必须逐条自检以下 7 问，任一「否」则不能标记完成。

> 输出方式（防仪式性刷屏）：七问为内部自检，不强制逐条输出；仅当某问为「否/存疑」时，输出该问编号+说明+补救动作。全部通过时对外只输出 §5.1 一行硬回执。

1. 禁止清单已确认：本次变更未触碰 §8 任何禁止项？
2. 已有 Bug 已排查：是否读过 debug-diary，确认未重复踩坑？改动涉及的模块，其历史 Bug 的回归测试用例是否已复跑，确认未复现？
3. 编译/测试通过 + 增量验证：编译通过？Lint/类型检查通过？测试分两层，**新功能测试是主位，回测是后台守卫**：
   - ① 新功能验证（主位，对外汇报主体）：本次新增/改动的路径（新端点/新函数/新交互）逐条单独验证——新端点必须发真实请求实测（状态码+响应结构），新逻辑必须加新用例；旧套件全 PASS 只证明无回归，不算新功能已测。实战教训（MetaData002）：新增 infer-mappings 端点零新用例零实测，旧套件全 PASS 照样标完成，用户一用即 405
   - ③ 部署/启动链验证（部署类改动强制）：docker-compose/entrypoint/初始化命令/Dockerfile 类改动 = 新功能，必须**与生产同构环境（容器）实测自定义命令逐条执行**（含输出证据），禁止仅本机 venv 验证；模拟部署验证必须产出「自定义命令实测清单」。实战教训（MetaData002 166 轮）：loaddata 条件命令 `from modeling.models import Domain` import 路径错误（INSTALLED_APPS 用 apps. 前缀），模拟验证只测了内置命令，容器内必 ModuleNotFoundError → 误判走 else → loaddata 撞唯一约束 → 容器崩溃前端全挂
   - ② 回测（后台守卫，降噪）：默认只跑本次改动波及模块的定向回归（按 prjm 影响分析圈范围）；仅跨模块改动/交付前/重大重构才跑全套。全绿只报一行「回归 N/N 通过」或并入「测」回执，**禁止每次任务例行汇报旧套件总数/通过率**（仪式性刷屏）；有失败才逐条列。无测试 → 问用户要不要加
4. 功能符合要求：回溯需求/故事线/功能清单交叉验证，是否符合用户要求？
5. 原有功能未丢失：对照改动模块在 `concept-feature-list.md` 登记的功能细项逐条点名，确认本次改动后仍全部保留？若有功能被删除或行为变更 → 是否已显式说明去向（移到哪/为何删/用户是否知情）？
6. 跨模块无破坏：依赖模块编译正常？接口签名/数据格式未破坏下游？有疑问 → AskUserQuestion 告知用户波及范围
7. 变更记录已同步：对应日记（design/dev/debug）是否已更新？无硬编码配置、无敏感信息泄露？（拓扑关系变化 → 同步更新 route_index 依赖拓扑）

7 问全部自检通过才能标记完成。

## 5.1 编码收尾硬回执（4 项，prjm 收尾强制）

> 实战教训（MetaData002，913 行 session 仅 4 次回执）：7 项长清单靠自觉必然死亡。砍成 3 项硬核，由 prjm 收尾环节强制输出；其余步骤由各自机制把守（进场靠 §1.1 hook 物理拦截、质量靠 §5 七问、复用靠 darc Step0），不再重复列举。

每次编码收尾必须输出一行硬回执：

`回执：闸[✓/⚠️] 记[✓/⚠️] 拓[✓/⚠️] 测[✓/⚠️]`

| 项 | 含义 |
|----|------|
| 闸 | 本次编码经 prjm 路由过闸（`.ai/.prjm-gate` 有效，hook 有 PASS 记录） |
| 记 | 对应日记（design/dev/debug）已更新 + 新决策/推翻已登记 constitution + 本次若有规则真拦住事已记 `.ai/telemetry/rule-hits.md`（无则免） |
| 拓 | route_index 依赖拓扑已核对/更新 + session 双层留痕（索引行+详情条目）已写 |
| 测 | §5 第3问新功能验证完成且证据已写日记：新增测试用例 N 条 / 实测请求 M 次（含关键响应）——这是回执汇报主体；回测全绿时不单独展开（并入本项即可），有失败才列出。本次无新增路径 → 标 ✓ 并注明「无新增路径」；纯文档/配置变更同 |

- 出现 `⚠️` → 停下补齐，不得标记完成；回执结果写入 session 索引行「完整性」字段。
- prjm 下次启动读索引时发现上轮 `⚠️` → 先提示补齐再接新活。
- 用户要求"复盘执行情况"时，prjm 统计索引「完整性」列中反复 ⚠️ 的同一项 → 作为流程优化输入（总漏 → 上 hook / 加硬确认）。
- 规则效能台账（减脂复盘数据源，已并入「记」项强制检查）：当某条规则/铁律真正改变了行为（拦住一次违规动作、纠正一次错误方向、迫使改变方案）时，向 `.ai/telemetry/rule-hits.md` 追加一行（日期/条款/事件摘要/影响）。只记真拦住的，不记"走流程没问题"——否则台账变成仪式性刷屏，失去裁决价值。

> 与"拆 agent"的边界：防漏步骤靠本清单回执（留主线程、可确认、可追溯），不靠拆 subagent——subagent 自主隔离、不与用户确认、状态不接力，反而会漏掉进场确认与收尾回写。agent 只用于"卸重读取"（见 prjm 重活外包 4 项）。

## 6. 文档同步

代码变更后，必须检查并更新对应日记：
- 设计变了 → 更新 design-diary
- 逻辑变了 → 更新 dev-diary
- 遇到已知问题 → 更新 debug-diary
- 模块边界变了 → 更新 concept-architecture.md

## 7. 防幻觉

AI 必须基于文件中的事实做事，不允许猜测：
1. 不猜就读：不确定时先读相关文件（diary/代码/架构文档），读了再说
2. 结论可追溯：AI 的每个技术结论必须能追溯到具体文件或代码。无法追溯 = 猜测，必须标注"我不确定"
3. 不确定就问：宁可多问用户一句，不可自作主张
4. 工程事实源优先：回答环境/依赖/版本/构建/部署相关问题前，必须先读工程配置文件（`package.json`/`pom.xml`/`build.gradle`/`requirements.txt`/`go.mod`/`Dockerfile`/`.env`/CI 配置等），以文件实际内容为准，禁止凭记忆或惯例猜测版本号、脚本命令、端口、路径
5. 运行态现状核对：读写数据库记录、判断进程/端口存活、依赖环境变量实际值之前，必须先查当前实际状态（查库/实测/读 `.env` 实际生效值），禁止信任上一轮日记或代码里"当时设置的值"。实战教训（MetaData002 admin 密码事故）：同一密码被多轮 AI 分别写成三个不同值，从未有一轮核对数据库实际存储值，分叉被冻结多轮无人发现
6. 三态确认纪律（适用于一切向用户的确认/AskUserQuestion，堵"看不懂而乱点=假确认"）：用户在确认点的状态分三种，AI 必须区别对待，禁止把三种状态都当成"用户已确认"：
   - 看得懂且能拍板 → 正常锁定
   - 看得懂但拿不准 → 两阶具象化（方法同 §11.1 第3条：先列 2-3 个具体事例帮判断；仍不确定 → 走验证探针/承载点出口）
   - 看不懂 → 换说法重讲：先讲后果（选 A 以后会发生 X）、打比方、算代价，禁止重复原话敷衍；仍看不懂 → 不逼拍板，AI 按用户声明过的偏好（如偏向治本）做**暂定默认**，且必须：① 显式声明"此为 AI 暂定决定，用户随时可反悔"② 仅限反悔代价小的决定；不可逆决定禁止暂定默认，只能缓做或拆成可反悔小步 ③ 记入 session-detail 并标记对应决定点，供日后整体反悔
   - 大白话义务：重大决定的问题必须先讲后果再讲方案，技术术语只能当补充不能当主语
   - 逃生门：每个确认问题必须含"再想想/看不懂"类逃生选项，选了不追问不施压
7. 验证环境同构原则：涉及容器/部署/环境差异的改动，验证必须在与生产同构的环境执行（容器内/同版本依赖），**"本机通过 ≠ 容器通过"**——import 路径、环境变量、路径、依赖版本都可能不同；无法容器实测时，必须显式声明验证环境差异并列出风险点。实战教训（MetaData002 166 轮）：条件命令本机从未在容器内跑过，`from modeling.models` 在容器必然失败却无人发现

## 8. 禁止清单（AI 绝不能做的事）

> 以下条目是经验总结的**绝对禁止行为**。违反将被视为严重错误。

### 代码底线
- ❌ **永不擅自删除代码**：删除前必须备份或标记 Deprecated，不可直接移除；任何删除/大幅改写必须在 dev-diary 记录「删了什么 / 为什么 / 影响谁」，让功能变动可追溯
- ❌ **永不修改已发布的接口签名**：只能新增重载，不改方法名/入参/返回值
- ❌ **永不自行引入新依赖**：必须先确认兼容性并 `AskUserQuestion` 确认
- ❌ **永不复制粘贴未读代码**：必须先 `read_file` 理解上下文，再适配使用

### 架构底线
- ❌ **永不擅自改变项目目录结构**：build/output/deploy 路径不可移动、重命名或重组
- ❌ **永不硬编码配置**：IP/端口/密码/Token 必须走环境变量或配置文件
- ❌ **永不吞掉异常**：`catch` 必须至少打日志，或向上抛出业务异常
- ❌ **永不引入不必要的中间件**：优先走简单方案，分布式中间件需用户确认

### 协作底线
- ❌ **永不跳过 prjm 路由直接编码**：任何代码变更前必须已经 prjm 路由、已用 `Skill` 加载对应技能、已做影响分析（见 §1.1）；prjm 不得自己代办子技能的活，未路由/未加载技能就改代码 = 违规
- ❌ **永不连续超过 3 步不汇报**：阶段性确认方向，避免跑偏
- ❌ **永不单次修改超 3 个无关文件**：拆成多次任务，每任务聚焦一个模块
- ❌ **永不忽略版本**：写代码前先确认 JDK/框架/依赖版本

### 幻觉底线（补充 §7）
- ❌ **永不猜工程事实**：依赖版本、构建脚本、启动命令、端口、部署路径必须以 `package.json`/`pom.xml`/`Dockerfile` 等配置文件实际内容为准，禁止凭记忆作答
- ❌ **永不编造未读内容**：未 `read_file` 的接口/代码/文档，一律视为"未知"
- ❌ **永不把"参考建议"当"强制结论"**：必须区分推荐和强制，不确定时标注
- ❌ **永不编造"为什么"**：未读设计文档/日记时，禁止解释历史决策原因

### 一致性底线
- ❌ **永不让同一配置事实分叉存放**：密码/端口/开关/密钥等同一事实禁止散落在代码默认值、脚本、日记多处各自为政；必须指定唯一主副本（环境变量或单一配置文件），其余位置只能引用主副本，禁止各写各的值
- ❌ **永不写不幂等的初始化脚本**：创建用户/初始化数据类脚本必须写成幂等收敛（已存在则更新/跳过并提示），禁止"仅首次创建时生效"——否则后轮修正永远无法收敛，分叉被永久冻结
- ❌ **永不放任存量覆盖性机制**：启动链/定时任务中"每次运行覆盖 DB 数据"的存量机制（如每次启动 loaddata 覆盖配置）必须审计治理——幂等化（已存在则跳过）或彻底移除，二选一，禁止以"历史遗留"为由放任；实战教训（MetaData002 166 轮）：每次启动 loaddata 覆盖服务器配置（用户界面改的 inner/conditions 被还原）+ 撞唯一约束中断启动链，3 个月无人治理直到出事

### 安全底线
- ❌ **永不输出敏感信息到日志**：密码、Token、身份证、手机号必须脱敏
- ❌ **永不注释掉权限校验**：测试用 Mock 用户，不绕过权限控制
- ❌ **永不拼接 SQL**：必须用参数化查询或框架的安全占位符

## 9. 复制主义（复用 > 创造）

核心理念：杜绝重复造轮子。写任何代码前必须先做复用优先扫描（详见 darc 编码 Step 0）：

1. 先查后写：先读 `REUSE_CATALOG.md` + `STYLE_GUIDE.md`，有现成就用，没有才写
2. 按骨架复制：按 STYLE_GUIDE 骨架写，只改业务表名/字段名，结构与模板一致
3. 扩展 > 新建：现有工具"差不多但不够用"时，优先扩展（新增可选参数/返回字段/重载），**不可复制改名另建**（如现有出参 AB、需要 ABC → 扩展成 ABC，而不是新建一个）；仅当扩展会破坏现有调用方或语义完全不同时才新建
4. 新物种必打样：遇到首次出现的技术栈/框架/模块范式（"新物种"）→ 暂停 → 先打样产出三大件/增量更新 STYLE_GUIDE → 再继续
5. 存量项目必回填打样（堵"触发点永久错过"漏洞）：项目已有代码但 `output/darc/` 无三大件 → 首次路由到编码时**禁止静默裸写**，必须先做回填打样：从现有代码提炼三大件（扫码起草可派 subagent，主线程确认落盘），用户确认后才继续本次编码。实战教训（MetaData002）：打样只挂在"第一个模块"上，存量项目永远不触发，复用生态 3 个月零运转。

> 与 §8 代码底线"永不复制粘贴未读代码"不矛盾：本处复制的是项目自己沉淀的可信骨架/工具；§8 禁的是复制未理解的外部代码。

## 10. 交付验收关卡（系统交付质量门）

交付物交付前必须经 uxqa 完成状态验收（四维核查：需求落地/流程落地/产品落地/体验落地 → 产出整改清单；纯后端无界面时体验维度标 N-A，其余三维仍必查）：

1. **整改清单未闭环禁止交付**：`output/uxqa/rectification-list.md` 存在 P0/P1「待整改/整改中」项时，禁止标记交付完成
2. 设计评审意见须落实：uxqa 设计评审关下发的开发约束（`output/uxqa/ux-review-[module].md`），编码时必须执行
3. P0 阻断：P0 项（阻断交付）必须整改闭环；P1 应改；P2 建议
4. 存疑必问：验收中实现与文档不一致、无法判定 Bug 还是预期、需求有歧义、涉及产品取舍 → 必须问用户，禁止自行下结论放行
5. 对抗验收前置：uxqa 判定"可交付"后、交付回执发出前，必经一轮 adqa 对抗验收（证伪式：找 checklist 之外的事）；adqa 无存活质疑或存活项已裁决闭环，才可发出交付回执。跳过 = 违反交付闸门

> 与 §5 分工：§5 完成前自检管代码正确性（编译/测试/跨模块/回归），§10 管交付完成度（需求/流程/产品是否真落地 + 体验合理性）。两关卡并列，均通过才可交付。

## 11. 重大方向锁定与架构可变性（防"编码后推翻"级返工）

**重大方向问题** = 数据流向（单向/双向同步）、存储模型、模块边界、核心交互范式级别的决策。此类决策被推翻的代价是跨栈删几百行，必须双轨防护：

**方向判定表（强制显式作答，堵"没意识到是重大方向"）**：每个新需求/改造任务开场，prjm 必须逐项回答是否触及上述四类，结论记入本次 session-detail（"不触及"也要写一句判定依据）；任一项命中 → 必走 §11.1 全流程。判定表静默跳过 = 流程违规（prjm 下次开场回溯核验）。

### 11.1 编码前循环 checklist 锁定（扼杀在前期）

重大方向未锁定前**禁止编码**。锁定不是一句 AskUserQuestion 完事，而是循环确认到双方同步：

1. AI 先输出「方向理解清单」：要做什么 / 明确不做什么 / 边界在哪 / 波及哪些模块，逐条编号
2. 用户逐条 ✓/✗/?；出现 ✗ → 修正清单重发；出现 ? → 按第 3 条两阶具象化处理；循环直到全部 ✓ 或 ? 已落定出口才开工
3. 用户说"不确定/答不上来" → **两阶具象化，第一次不确定 ≠ 真不确定**（通用三态确认纪律见 §7 第6条，本节为方向锁定场景细化）：第一阶 AI 必须列 2-3 个具体事例/场景（若该假设成立/爆掉你将面对什么，各带代价与不可逆点）或 2-3 个候选方向，帮用户具象化后再请裁决，禁止抛开放式问题等用户自己想；第二阶用户看了事例仍说不确定 → 才是真不确定，走第 2 条 ? 分流（廉价验证探针 / 落 §11.2 承载点），禁止硬锁与逼供
4. 输出清单后必经 adqa 质疑关：逐条攻击隐含假设（上限5条、每条自带一步可跑的证伪方法），裁决结果随清单一起锁定（rule §10 分工注：adqa 不代替用户裁决，只给攻击与验证要求）
5. 锁定结论记入 constitution 架构级决策区（含 ? 分流去向：待验证/承载点文件清单），并**逐字内嵌 adqa 硬回执行**（`回执：质[…] 伪[…] 锁[…]`）——该行是质疑关真跑过的唯一可核验凭证，prjm 下次开场回溯 grep 此行，缺失 = 上轮方向锁定跳过了质疑关，报警补齐（rule §11.1 与 adqa 时点 A 的闭环闸门）

### 11.2 架构为方向变化留活口（承认用户"操作后才有感觉"）

循环 checklist 也挡不住用户用过之后改主意——这是合理的，架构必须消化它：

- 方向性逻辑必须收敛到可替换单点（独立引擎/服务模块/单文件），**禁止散布**在序列化器、视图、前端组件多处
- darc 设计日记必须登记「方向承载点」文件清单：该方向推翻时要动哪几个文件
- 验收标准：方向推翻 = 替换/删除单点文件 + 改调用处开关，而不是跨栈删 900 行

## 12. 母本/副本双份维护（防"改一处忘同步"的静默分叉）

`prjm-rules.md` 母本与各项目的 `.qoder/rules/prjm.md` 副本、`prjm-gate.sh` hook 的双份文件，属于"同一事实两处存放"的高危结构，纪律不可靠自觉，必须硬校验：

1. 改动母本或 hook 后，必须立即 `Copy-Item` 同步到所有项目副本（一个都不能漏）
2. 同步后必须哈希比对双侧一致，禁止只比对字节大小（大小相同内容不同照样分叉）：
   ```powershell
   Compare-Object (Get-FileHash 母本路径).Hash (Get-FileHash 副本路径).Hash   # 无输出 = 一致
   ```
3. 比对结果必须写入本次回执/日记（如「规则已同步：hash 一致」）；比对不一致 = 任务未完成，禁止收尾
4. 读规则时若发现副本与母本表述不一致 → 立即停下核对双侧文件，禁止带分叉继续执行
